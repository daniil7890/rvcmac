## 0. P0 — контроллер уровня очереди (17.11.2026, статус обновлён 25.11.2026)

Статус: спроектирован и реализован **офлайн в `QueueModel` (RVCMacCore)**, 17 юнит-тестов
(6 на контроллер, 4 на реплей и гейт); движок НЕ правился. **Перенос в движок заблокирован
до калибровки реплея** (см. «Реплей и калибровочный гейт» ниже): модель не воспроизводит
уровень очереди живой сессии, значит, и выигрыш контроллера на ней — не оценка.

**Обоснование числом** (живая сессия A b50_e530_cf50, 116.8 с, BENCHMARKS 17.11):
рейчет подтверждён — pipeline p50 42.5 → 85.2 мс, равновесие очереди ~60 мс = 80% порога
подрезки 1.5×50 = 75 мс; 45% алгоритмического выигрыша стадии A (−30.6 мс) съедено очередью.
Удержание outputQueue на prefill (25 мс) даёт pipeline ≈ 25 + 24.5 ≈ 50 вместо 85 →
e2e ≈ 204 (**−35 мс**); плюс стадия B (cf30, alg замерен 85 против 104.5, BENCHMARKS 17.11)
→ ~185 (ещё −19.5). Приоритет P0 — не сравнение величин: реалистичный модельный выигрыш
контроллера (−7.5…−12, честный пол ниже) МЕНЬШЕ конвертации B (−19.5), но контроллер
устраняет сам механизм рейчета, съедающий выигрыш любой конфигурации, и не требует новых
моделей; B уже прошла офлайн-гейты, её живой замер всё равно после контроллера.
−35 — верхняя граница, сравнение величин — только после живого замера.
**25.11.2026:** равновесие найдено (85 мс с t = 33 с, дрейф +0.6 мс за 84 с), «модельный
выигрыш −7.5…−12» получен на синтетике ±1 мс и реплее с незакреплённой геометрией —
**не оценка, а иллюстрация**. Порядок «контроллер, потом B» перевёрнут, см. §7.

**Честный пол (офлайн-replay живого CSV, 2328 блоков, b50/44.1k/буфер 512):**
- Модель воспроизводит базу: underrun 19 = живые 19; pipeline p50 71.4 (живые 85.2 —
  модель занижает базу на ~14 мс, дельта контроллера — модельная оценка, не живой прогноз).
- Очередь нельзя удержать на чистом prefill: записи приходят раз в блок (50 мс), между ними
  уровень не должен опускаться ниже одного буфера (11.6 мс) + запас на джиттер. Пол outputQueue
  ≈ буфер + запас. Цель 75 мс (1.5 блока), band block/8: pipeline p50 63.9 (−7.5), underrun 20 ≈ 19.
- Ниже пола задержка покупается underrun'ами: цель 62.5 мс → pipeline 49.8, но underrun 104 (×5.5);
  цель = prefill → underrun каждый блок (2322). Критерий «pipeline p50 ≤ prefill + block_total + 5
  без роста underrun» на живом джиттере достижим только у пола; **оценка −35 мс — верхняя граница**
  (outputQueue → prefill), реалистичный выигрыш по модели −7.5…−12 мс, живой — после замера.
- Синтетика b100 (буфер 10 мс делит блок, джиттер мал): критерий выполнен — steady pipeline
  100 → 90 ≤ 50 + 36 + 5 = 91, underrun 1 = 1, уровень 115 → 105 мс (рейчет снят).

**Дизайн (реализовано в QueueModel):**
- `Controller(target, band)` в Config; по умолчанию nil — прежнее правило maxFill, все старые
  тесты не тронуты.
- **Целевая фаза после underrun:** рекомендуемый target = blockOut + prefill — первый сэмпл
  свежего блока ~prefill впереди головки чтения (outputQueue ≈ prefill). Подрезка срабатывает и на
  первом колбэке после повторного prefill: catch-up-всплеск больше не задаёт новую фазу — это и
  убивает рейчет.
- **Гистерезис:** подрезка только при уровне > target + band, до target; band меняет частоту
  подрезок, но не удерживаемый уровень (тест).
- **Trim при RTF < 1:** становится регулятором уровня — периодические подрезки до target вместо
  разовой до frames + maxFill. При RTF ≈ 1 catch-up нет, уровень не достигает target + band,
  подрезки не срабатывают (тест).
- **Пол target:** > blockOut + outputBufferFrames, иначе очередь между записями опускается ниже
  буфера → underrun каждый блок (проверено).
- Критерий приёмки: pipeline p50 ≤ prefill + block_total + 5 мс без роста underrun —
  **снят 25.11.2026**: выведен из верхней границы −35, а не из модели; на живом джиттере
  промах 18–23 мс (BENCHMARKS, «Реплей живого CSV»).

**Реплей и калибровочный гейт (25.11.2026).** В `QueueModel` добавлен режим `replay`
(время блока = `block_total_ms` живого CSV, момент записи = `t_sec`) и гейт
`Calibration`: baseline-реплей обязан воспроизвести очередь p50, подрезки и underrun живой
сессии в пределах 20% каждое, иначе модель не калибрована и контроллер не оценивается.
- «Модель воспроизводит базу: underrun 19 = живые 19» (17.11) **текущим реплеем не
  воспроизводится**: при буфере 512 и фазе 0 — underrun 25 (живых 19, +31.6%), очередь
  p50 33.5 против 60.3 (−44.5%), подрезки 24 против 22. Геометрия прогона 17.11 в документе
  не закреплена, сверить нельзя.
- Уровень очереди решает выходной буфер, который в сессии не залогирован: 18.6 мс при 64
  кадрах → 68.3 при 2048. Гейт не может ни пройти, ни провалиться окончательно, пока
  буфер неизвестен.
- Жёсткие условия переноса пре-регистрируются сейчас: underrun не хуже baseline-реплея;
  склейки не чаще 0.19/с (уровень сессии A, на котором слушали A3); термалка nominal.
  Количественная цель по pipeline — из калиброванного реплея.
- **Guard при переносе обязателен** (из W2): prefill > blockOut в IOProc без guard
  оставляет хвост, который никогда не наберёт prefill; в `QueueModel` это случай
  «tail drains when prefill exceeds one block», тест есть (`testTailDrainsWhenPrefillExceedsOneBlock`).
  В движок переносится вместе с этим тестом на реальном IOProc.

**Перенос в движок (следующий шаг, не сделан):** A3-склейка на подрезке уже есть
(AudioIO.swift: equal-power кроссфейд головы выброшенного региона, бленд через колбэки) —
вопрос переноса не в отсутствии склейки, а в её поведении при частоте подрезок контроллера
(~раз в band кадров): проверить, при необходимости рамп/ограничение частоты. `limitBacklog`
движка в модели нет — catch-up там ограничен, модельные счётчики подрезок на всплеске — верхняя
оценка (ограничение модели из раздела «Залипание очереди после A2»).

**Пересмотр доминирования B' (17.11.2026).** Равновесие очереди задаётся потолком подрезки
1.5×block: у A 75 мс, у B' 90 мс. При наблюдаемом равновесии ~80% потолка: A ~60 мс, B' ~72 мс —
**больший блок может уползти ВЫШЕ**, и выигрыш B' по alg (100 < 110) съедается очередью. Прежний
вывод «B' лучше A по всем осям» **снят как факт, остаётся гипотезой** до живого замера. С
контроллером потолок больше не задаёт равновесие — тогда доминирование B' по alg/бюджету/prefill
снова становится релевантным, но проверять только замером.

## 2. Адаптивная стадийность

Полная сетка заменена адаптивной: каждая следующая стадия зависит от результата предыдущей,
лишние конвертации не делаются.

**Стадия 1 — b80_e300 (выполнена 15.11.2026): НЕ прошла по F0.** 03_loud CPU превысил
пре-регистрированный порог медианы на сидах 2/3 (повторное нарушение, засчитано); e300
ухудшает 03_loud по всем трём F0-метрикам (среднее по 10 файлам это скрывает). Направление
урезания контекста отклонено; лестница ниже сохраняет контекст.

**Стадия 1c — b80_e340_cf50 (F=48): СНЯТА с критического пути (15.11.2026).**
Гипотеза кратности опровергнута (F=66 на ANE, см. §5); тест выравнивания не нужен.
Триггер fallback F=44 — в бэклоге P2 (per-op diff дампов, без конвертаций).

**Новая лестница (15.11.2026): F фиксирован, extra бесплатен.** Все конфигурации F=64,
N=10240, shared/N10240 переиспользуется (конвертится только synth). Контекст 640 мс
(F×10) не меняется → риск не потеря контекста, а рост склеек 12.5 → 20/с и укорочение
кроссфейда. Duty cycle CPU 34% → 50% — термалку проверять вживую.

| Ступень | Конфигурация | F | alg, мс | бюджет, мс | prefill, мс | Что изолирует |
|---|---|---|---|---|---|---|
| база | b80_e500_cf50 | 64 | 140 | 80 | 40 | — (живой замер e2e 258 мс) |
| A | b50_e530_cf50 | 64 | 110 | 50 | 25 | ТОЛЬКО блок (cf не меняется) |

alg = block + cf + sola − offset; extra не входит. F = block_f + 1 + extra_f + cf_f:
A: 5+1+53+5 = 64; B': 6+1+54+3 = 64; B: 5+1+55+3 = 64.

**B' доминирует A по alg (100 < 110), бюджету (60 > 50) и подушке (prefill 30 > 25) — но это
доминирование СНЯТО как факт (17.11.2026, §0):** равновесие очереди задаётся потолком подрезки
1.5×block (90 против 75 мс), больший блок может уползти выше, и выигрыш по alg съедается очередью.
Остаётся гипотезой до живого замера. От B отличается только блоком (cf=30 общий); от A — блоком и
cf, то есть это кандидат, а не чистая изоляция. Все F=64, N=10240, shared переиспользуется.

**Риск prefill.** Уровень очереди ~ prefill + обработка. На b50 prefill 25 мс против
40 мс на b80 → подушка на джиттер меньше на 15 мс при том же живом джиттере
(p99−p50 = 16.2 мс по steady-state, 24.5 мс по агрегату) → underrun может стать больше
(на b50 запас над steady-джиттером ~9 мс, над агрегатным ~0.5 мс). У B' подушка 30 мс —
промежуточная. Прогноз живого p99 стадии A (BENCHMARKS, «Steady-state…"): 51.9–62.1 мс
при бюджете 50 — офлайн-прохождение не гарантирует живой гейт.

**Ограничение доминирования B'.** Доминирование по alg/бюджету/prefill не распространяется
на block_total и качество. «Окно 600 > 580» — это block+extra, **не окно вычислений**:
F=64 (640 мс) одинаков у A/B'/B; R = block_f+1+cf_f: A=11, B'=10, B=9 — декод у B/B'
дешевле. Рост p99 стадии A против базы (32.7 → 39.1 мс) объясняется плотностью блоков
(12.5 → 20/с) и duty cycle (31% → 47%); точный механизм не установлен. Прогноз p99 для
B/B' — только по факту после конвертации, не экстраполяцией. cf30 < cf50 — отдельный
риск качества (изоляция в стадии B).

**Резерв: b70_e530_cf30** (F = 7+1+53+3 = 64, alg 110 мс, бюджет 70, prefill 35) —
кандидат, если B' не пройдёт живой p99. Формы: phone/pitch [1,64,…] и audio [1,4400]
идентичны A; noise [1,192,37] против [1,192,35] у A (T = block_f+30) — не полностью
идентичны, конвертация только synth, shared/N10240 переиспользуется.

**Гейты стадий A/B/B'/резерва:** пофайловые абсолютные пороги пре-регистрации (§6) — они
конфигурационно независимы; bound-сетка ОБЯЗАТЕЛЬНО по блоку конфигурации
(`--block-ms 50` для A/B, `--block-ms 60` для B', `--block-ms 70` для резерва);
перф p99 ≤ 0.8 × blockMs (A/B: 40 мс, B': 48 мс, резерв: 56 мс); правило одиночного
срабатывания. Режим: только CPU (ANE+GPU — pessimization ×1.7).

**Прежние стадии e300/e400 ОТКЛОНЕНЫ** (1b b50_e370_cf50, 2 b50_e390_cf30, fallback
b80_e400) — резали контекст; стадия 1 не прошла по F0 на 03_loud. b100_e300/e400 отложены.

Сетка cf50 на стадии A не меняется (аргумент про конфаунд принят): при b50 cf50 == block —
граница клампа D3; cf > block внёс бы кламп-конфаунд. Стадия B (cf30 < block) — после A.

Голос gaechkatm (референсный), pitch 12, index 0.75, protect 0.33, gate −60. Сиды 1 и 2.
Весь TestAudio (10 файлов), pacing fast, warmup 10. На стадию A: 2 × 10 = 20 прогонов (CPU).

## 3. Протокол качества: абсолютные метрики

Существующие пороги (`BENCHMARKS.md`, «Пороги качества») подобраны как **разности против
выхода 100/500/50** и кросс-конфигурационно не применимы: выходы разных конфигураций легитимно
различаются (другой контекст → другой сигнал), и разность измеряла бы различие конфигураций,
а не регрессию. Поэтому сравнение МЕЖДУ конфигурациями — только по абсолютным метрикам,
каждая конфигурация проверяется независимо.

**Жёсткие гейты (на файл, абсолютные):**
- `bound_clicks = 0` и `bound_jumps = 0` — щелчки/скачки на границах блоков (определения из
  `scripts/quality_gate.py`). Это главный критерий: контекст не должен ломать стыки.

**F0 относительно входного сигнала (не относительно выхода другой конфигурации):**
- pyin по входу и по выходу; кадры, voiced в обоих; ошибка в центах:
  `err = 1200·log2(f0_out/f0_in) − 100·pitch` (pitch 12 → ожидаемое удвоение).
- Метрики: медиана |err|, p95 |err|, доля |err| > 50 центов, доля |err| > 600 центов
  (октавные обороты — отдельно, см. ограничение ниже).
- Предлагаемые абсолютные пороги (предложение, калибровать после замера референса e500 этим
  же протоколом): медиана |err| ≤ 50 центов, доля |err| > 100 центов ≤ 10%. Пороги фиксируются
  до прогонов кандидатов, чтобы не подгонять под результат.

**Наблюдаемые (без гейта):** клики суммарно, gain_db относительно входа, len_err, gaps,
алгоритмическая и pipeline-задержка конфигурации, распределение block_total.

**Гейт производительности:** p99(block_total) ≤ 0.8 × blockMs в целевом режиме на всём
TestAudio; max и число блоков сверх бюджета — в отчёт.

**Правило одиночного срабатывания:** нарушение на одном сиде → проверка на втором;
считается только повторившееся (оба сида прогоняются сразу).

## 4. Чего этот протокол НЕ доказывает

- **Перцептивное качество, тембр, похожесть на спикера** — нет прослушивания и нет
  speaker-embedding метрики; абсолютные F0 и стыки доказывают только корректность высоты и
  отсутствие граничных артефактов.
- **Что e300 «не хуже» e500** — эквивалентность конфигураций не устанавливается; протокол
  проверяет абсолютный пол, а не сравнительное качество. Разный контекст может звучать
  по-разному при одинаковых абсолютных метриках.
- **Живая стабильность** — тепловые режимы, underrun на реальных устройствах, дрейф,
  длинные сессии: офлайн-харнесс этого не видит.
- **Валидность самой F0-метрики** — pyin даёт октавные ошибки (аудит 10.7); доля оборотов
  > 600 центов может отражать ошибку метрики, а не конверсии.
- **Обобщение на другие голоса/питчи/языки** — один голос, pitch 12.

- **Порог запрета b50: b50 запрещён, если замеренный p99(block_total) > 40 мс** (80% бюджета
  50 мс — нет запаса на джиттер); при p99 > 50 мс underrun систематические. Оценка b50_e400
  p99 ~39 мс — пограничная, решение только по замеру.

**Оговорка к модели:** масштабирование fcpe ∝ блоку спорно — питч считается по окну
(fcpe видит весь контекст), а не по блоку, и при уменьшении блока доля fcpe может не упасть.
Оценка p50 16.8 мс для b50_e300 — **оптимистичная граница**: f0/excitation могут остаться на
уровне b80. Решение только по замеру после конвертации.

**Выводы:**
1. Нулевое сравнение даёт ровно 0 — реализация протокола корректна.
2. Межсидовый шум (≤ 10 центов по медиане, октавных оборотов 0) существенно ниже порога

   величиной > 10–20 центов отличима от шума метрики.
3. Предложенные абсолютные пороги (медиана ≤ 50, gt100 ≤ 10%) **не проходят сам референс**:
   gt100 в среднем 13–15%, до 39–46% на `03_loud`; медианы до 70–90 центов. Это не шум
   метрики (межсидовый разброс мал), а реальное отклонение F0 на проблемных файлах
   (аудит 10.7) плюс октавные ошибки pyin на стороне входа. Калиброванные по референсу
   значения — это **абсолютный пол текущего пайплайна, а не целевое качество**; они
   фиксируются до прогонов кандидатов: на файл — медиана ≤ 90 центов, gt100 ≤ 0.46,
   октавы ≤ 0.22; в среднем по 10 файлам — gt100 ≤ 0.15; на «чистых» файлах
   (кроме `03_loud`/`07_high`) — медиана ≤ 30 центов.

**Гейт регрессии.** Абсолютный пол не ловит регрессию внутри допустимого коридора, поэтому
кроме пола сохраняется сравнение **внутри одной конфигурации**: кандидат против своего
эталона (тот же режим/сид) по существующим порогам BENCHMARKS («Пороги качества», разности).
Пол отвечает на вопрос «не хуже ли текущего пайплайна вообще», разностный гейт — «не стала
ли хуже данная конфигурация». Оба обязательны при наличии эталона конфигурации; для новой
конфигурации без своего эталона работает только абсолютный пол (пофайловые пороги ниже).

**Ограничения метрики:**
- Лаг-поиск 0..200 мс клипует. Для сетки e300/e500 при b50/b80/b100 диапазона хватает
  (оценка алгоритмической ~105/135/155 мс для cf50), но b150_e500_cf100 (255 мс) вне диапазона —
  метрика соврёт молча. В `f0_vs_input.py` добавлена явная проверка: `lag_at_boundary`
  (лаг 0 или 200 мс) и предупреждение в stderr; результат с этим флагом при pitch ≠ 0
  не интерпретировать без расширения диапазона (лаг 0 для само-сравнений ожидаем).
- Лаг выбирается по минимуму медианы **отдельно для каждого сравнения** → оптимистическое
  смещение, у разных конфигураций разное; межконфигурационные разности медиан частично
  отражают разницу лагов, а не качества.
- `bias` в quality_gate — медиана **свёрнутой** по октаве ошибки, в f0_vs_input —
  **несвёрнутой**; напрямую не сравнивать (`wrap_median` при этом совпадает).
- Теоретический пол метрики: квантование F0 в RVC (256 mel-бинов 50–1100 Гц) даёт
  ±13 центов на 200 Гц и ±8 центов на 400 Гц; сетка pyin resolution 0.1 = 10 центов.
  Суммарный пол ~**±15–20 центов** — требовать точности ниже нельзя.

### Пре-регистрация пофайловых порогов (15.11.2026, ДО прогонов кандидатов)
