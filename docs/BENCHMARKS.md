## Пороги качества (предварительные)

**Статус: предварительные.** Подобраны на одном голосе (`gaechkatm`) и синтетике (`TestAudio` из ElevenLabs). Пересмотреть после добавления живых записей с микрофона или второго голоса. Проверены только на данных, на которых подобраны.

Метрики считает `scripts/quality_gate.py`. Сравнение: кандидат минус эталон **той же конфигурации и того же режима**, на сидах 1 и 2 (сид по умолчанию равен 1). Эталон: `reports/quality-baseline-e725643/` (конфигурация 100/500/50). Для сравнения разных режимов (CPU и ANE+GPU) эти пороги не подходят.

| Метрика | Что сравниваем | На файл | Среднее по 10 файлам |
|---|---|---|---|
| Щелчки на границах блоков | абсолют, кандидат | 0 | сумма ≤ 1 |
| Скачки на границах блоков (`bound_jumps`) | абсолют, кандидат | 0 | сумма ≤ 1 |
| Щелчки всего | разность | ≤ +9 | ≤ +2,5 |
| F0, ошибка по модулю октавы (wrap-MAE) | разность | ≤ +35 центов | ≤ +8 центов |
| Доля F0 >50 центов, по модулю октавы | разность | ≤ +0,05 | ≤ +0,015 |
| Дрожание F0 | разность | ≤ +9 центов | ≤ +3 цента |
| Усиление/RMS активной части, модуль | разность | ≤ 0,35 дБ | ≤ 0,12 дБ |

**Правило одиночного срабатывания.** Если порог превышен один раз, повторить прогон на другом сиде и засчитывать нарушение, только если оно повторилось. Ориентировочная доля ложных тревог на полный прогон всех метрик — 5–15%.

**Правило покрытия задержки.** Перцентиль q задержки достоверен только при q < покрытие (доля блоков с измеренной задержкой). Неизмеренные блоки — не случайная выборка: resolvePending выбрасывает pending при подрезке очереди, а подрезка случается на backlog, то есть исключаются самые долгие блоки; хвост pending на момент Stop тоже не измеряется; строки без входа в pending (нет clock на старте, частичная запись) и батчи, отброшенные try-lock'ом экспортёра, остаются NaN. Поэтому p99 помечается недостоверным при доле неизмеренных ≥ 1%, p95 — при ≥ 5%, p50 — при ≥ 50%. В отчёте: `latency.latencyCoverage`, `latency.unreliablePercentiles`, счётчик `counters.unresolvedLatency`; в Диагностике — строка «Покрытие задержки» и пометка `*` у p99. Оговорка: live-покрытие считается от `recorder.total` (кумулятивно), отчёт — от строк, обрезанных capacity 40000 (~100 мин) и без warmup; на очень длинных сессиях значения могут расходиться. Инкременты счётчика в цикле воркера юнит-тестами не покрыты (цикл device-dependent) — инвариант зафиксирован здесь и в коде.

Порог щелчков на границах отдельный, потому что дефект gate из 24 граничных щелчков дал лишь +2,4 к общему счёту в среднем. Доля октавных кадров F0 — диагностика без порога. Абсолютные значения щелчков и F0 не означают число слышимых дефектов: детектор срабатывает и на чистой речи, pyin даёт октавные ошибки.

## Исправление тайм-аута stop, C2 (2026-11-13)

`VoiceEngine.stop()` больше не возвращает управление с живым worker: токен сессии и приватный семафор завершения на каждую сессию (`WorkerSession`), тайм-аут 3 с только сообщает о медленном выходе, join продолжается до сигнала. Запоздалый сигнал старой сессии не может удовлетворить новый stop.

Харнесс не использует `VoiceEngine` (гоняет `VoicePipeline` напрямую), поэтому C2 вне его пути обработки. Проверка: 7 новых юнит-тестов `WorkerSessionTests` (токены, join, медленный выход, запоздалый сигнал), `swift test` — 45 тестов, 0 падений; `swift build -c release --arch arm64` проходит; ревью `rt-audio-reviewer` — замечаний к RT-пути нет. Контрольный прогон харнесса до и после правки: `01_normal`, CPU, 100/500/50, 48 кГц, gate −60, сид 1, pacing fast — выходы побайтово совпали между собой и с эталоном `reports/quality-baseline-e725643/seed-1/cpu/01_normal`. Путь обработки не менялся; живая сессия не проверялась.

## Экспорт отчёта без блокировки воркера, B4 (2026-11-13)

Запись телеметрии на воркере (`recorder.append`, `setLatency`, чтение `total`) переведена на `withLockIfAvailable`: при занятом локе строка пропускается и считается в `Report.Counters.droppedRows`. Экспорт берёт под локом только плоский снапшот хранилища (`BlockRecorder.snapshot`, одна копия без построчных аллокаций), материализация строк и JSON/CSV — вне лока. `AppState.stop()` строит отчёт после `engine.stop()`: воркер уже завершён, отчёт видит все блоки; частоты и задержки устройств сохраняются после `io.stop()` (проверено по коду `AudioIO`). Старые отчёты декодируются: отсутствующие ключи counters получают дефолты.

Харнесс не использует `VoiceEngine` (гоняет `VoicePipeline` напрямую), поэтому B4 вне его пути обработки. Проверка: 7 новых юнит-тестов `BlockRecorderTests` (снапшот, независимость снапшота до и после wrap, try-lock, декодирование старых отчётов), `swift test` — 52 теста, 0 падений; `swift build -c release --arch arm64` проходит. ## Очередь «Щелчки», коммит 1: D2–D5 в VoicePipeline (2026-11-14)

Переходы bypass теперь непрерывны: вход — равномощный фейд от последнего услышанного сэмпла (post-gain), выход — SOLA от pre-gain якоря с gate-рампой, засеянной открытой. Применяемый кроссфейд ограничен блоком (cf = min(cfOut, blockOut)), параметр пользователя не меняется, фактическая длина показана в UI. Gain рамится на длине cf вместо скачка на границе; при NaN/Inf на выходе синтезатора блок заменяется тишиной с рампой от последнего сэмпла и считается в `Report.Counters.nanBlocks` (decodeIfPresent). Переходные функции вынесены в чистый модуль `Fade`.

Проверка: `swift test` — 66 тестов, 0 падений (11 новых `FadeTests`, гладкость стыков проверяется числом — максимальной разностью соседних сэмплов); `swift build -c release --arch arm64` проходит. Базовый прогон харнесса (`01_normal`, CPU, 100/500/50, 48 кГц, gate −60, сид 1, pacing fast) **побайтово совпал** с эталоном `reports/quality-baseline-e725643/seed-1/cpu/01_normal` — штатный путь (gain 1, bypass off, cf 50 < блока 100, NaN нет) не изменён. Сценарии харнесса (`--bypass-at/--bypass-off-at`, `--gain-at/--gain-to`, `--gain`) на громкой речи `03_loud`: шаг на границе блока 0.00000–0.00003 при якоре до 0.5, максимумы переходных окон не выше установившегося сигнала после перехода. Ревью `rt-audio-reviewer` в два круга: все WARNING закрыты (якорь вместо сыгранного хвоста, домены gain, outCount до applyGain, сброс якорей в NaN-ветке, gateRamp=cf на выходе). Новые пути покрыты юнит-тестами и сценариями харнесса; живая сессия не проверялась. Known edge (NOTE ревью): первый bypass-блок с укороченным выходом SRC (outCount < cf) — фейд может не завершиться в блоке; одноразовый на сессию, без краша; якоря при outCount == 0 сохраняются.

## Очередь «Щелчки», коммит 2: A2/A3/A5 в выходном колбэке (2026-11-14)

Underrun (A2): частичный буфер рамится к нулю нормализованной рампой 5 мс (первый сэмпл сохраняет предыдущую амплитуду — без ступеньки на границе колбэков), затем повторный prefill (блок/2 сэмплов) и возврат с рампой от нуля; рампы могут длиться несколько колбэков. Trim (A3): стык кроссфейдится 5 мс с головой discarded-региона на предаллоцированном буфере (префикс добит первым discarded-сэмплом, чтобы фейд стартовал точно со старого сигнала; на prefill-рампу splice не накладывается); trimFrames считает весь drop. A5: хвост выходного буфера за пределами produced frames зануляется (mono и interleaved). Все буферы выделены в `start()`, состояние только в `OutputCallbackState`; в IOProc нет аллокаций, локов, логов и retain/release. Размен повторного prefill — до blockMs/2 задержки после underrun — зафиксирован в аудите как осознанный.

Проверка: `swift test` — 68 тестов, 0 падений (13 `FadeTests`: рампы, стыки, частичный хвост, непрерывность границ); `swift build -c release --arch arm64` проходит. Харнесс не использует `AudioIO` — новые пути колбэка покрыты только юнит-тестами чистых функций; живая сессия с буферами 64/128 фреймов и спровоцированными underrun не проверялась (рекомендация ревьюера). Ревью `rt-audio-reviewer`: все WARNING закрыты (нормализация короткой рампы, splice до underrun-рампы, отсутствие splice на prefill, полный учёт drop).

## Залипание очереди после A2: проверка гипотезы (2026-11-14)

Гипотеза: после underrun и повторного prefill (0.5 блока) очередь остаётся на уровне prefill, потому что подрезка (порог 1.5 блока) может не сработать никогда. `QueueModel` приведён в соответствие с новым колбэком (сброс `started` при underrun → ожидание нового prefill; рампы и splice на учёт уровня не влияют — splice потребляет тот же drop), добавлен трасс уровня очереди на каждом колбэке. Симуляция: 60 с, b100, буфер 480 кадров, prefill 2400 (50 мс), maxFill 7200 (150 мс), stall +500 мс на t = 10 с; два режима воркера.

| Режим | До underrun (8–10 с) | Сразу после (11–12 с) | Через 30 с (40–42 с) | underrun | Подрезки |
|---|---|---|---|---|---|
| RTF 0.36 (CPU-подобный) | 55.0 мс | 115.0 мс | 115.0 мс | 1 | 7 |
| RTF 1.0 (ровно real-time) | 55.0 мс | 55.0 мс | 55.0 мс | 1 | 0 |
| RTF 1.0 ±1 мс (джиттер) | 60.0 мс | 60.0 мс | 60.0 мс | 1 | 0 |

**Вывод (честный): гипотеза в буквальном виде не подтвердилась** — очередь не залипает на уровне prefill. Но подтвердилось смежное опасение: **подрезка в установившемся режиме не срабатывает** (воркер привязан к приходу входа и не убегает вперёд), поэтому фаза очереди после underrun сохраняется неограниченно долго. При RTF < 1 catch-up-всплеск после stall подрезается, и уровень даже выше прежнего (115 против 55 мс) — новая фаза остаётся. При RTF ≈ 1 уровень не меняется (55–60 мс), подрезок нет ни до, ни после; джиттер ±1 мс вывод не меняет. Прежняя формулировка аудита «задержка возвращается к штатной по мере подрезки» опровергнута и исправлена. Правки движка не делались (только модель и тесты); вопрос о целевой фазе очереди после underrun остаётся открытым.

Ограничение модели (ревью): catch-up воркера в модели не ограничен `limitBacklog` (в движке при отставании > 4 блоков вход пропускается до 2 блоков), поэтому 7 подрезок на всплеске — верхняя оценка, артефакт модели; реальный всплеск из 2 блоков даёт ту же установившуюся фазу ~115 мс (проверено ревьюером вручную). Счётчики подрезок и per-block задержки в окне catch-up не faithful; установившийся вывод устойчив. Также модель не считает underrun на естественном стоке в конце потока и считает блок, закончившийся ровно в момент колбэка, «успевшим» (knife-edge RTF 1.0 проверен джиттером). Тесты: `QueueModelTests.testUnderrunWaitsForNewPrefill`, `testQueueLevelAroundUnderrun`, `testDegenerateConfigDoesNotHang`.

Underrun считается в кадрах недоданного буфера (`frames − got` за колбэк, AudioIO.swift),
поэтому среднее число кадров на событие не может превысить размер буфера:

| Сессия | underrunFrames / события | кадров на событие | Вывод |
|---|---|---|---|
| база b80 | 3200 / 50 | **64.0 ровно** | буфер 64 — подтверждено |
| A b50 | 3924 / 19 | **206.5** | буфером 64 не объясняется |

**Вывод:** «underrun ×2.6 к базе» (17.11) **снято**. Сравнение некорректно по трём
причинам сразу: другое выходное устройство, другая частота выхода (48 против 44.1 кГц),
другой буфер. Частота underrun зависит от буфера напрямую (меньше буфер — чаще недобор
до prefill), сравнивать её можно только при одном буфере.

**Проверка по app.log:** строки «Выходной буфер (dev)» в логе **нет ни для одной
сессии** (grep, 0 совпадений). Ключ `outputBufferFrames` в `UserDefaults` сейчас
отсутствует (`~/Library/Preferences/RVCMac.plist`, записан 17.11 11:52 — старт сессии A),
то есть dev-переопределение буфера в сессии A не применялось и могло не применяться в базе
(переопределение device-global и не восстанавливается при Stop). **Размер буфера каждой
сессии неизвестен.** Сейчас все присутствующие устройства отдают 512 кадров, но это не
доказательство для 17.11: устройство и его настройки могли измениться.

**Подрезки сравнимы:** 1.21 мс/с (A) против 2.09 мс/с (база) = ×0.58 — нормировка на
время секунды аудио, от буфера не зависит.

**Пробел телеметрии:** `EngineStats` знает `inputBufferFrames` / `outputBufferFrames`
(VoiceEngine.swift), DiagnosticsView их показывает, но в JSON отчёта и в лог они не
попадают. Пока размер буфера не записан в отчёт, никакая модель очереди (включая реплей
в «Реплей живого CSV через QueueModel») не может проверить свою геометрию по архиву.
Правка — добавить оба значения в `Report.ConfigInfo`; движок и IOProc не затронуты,
в этом заходе не делалась.

### б) Память: +19.8 МБ к базе — открытый вопрос
