# RVCMac 0.3.0 — Adaptive Real-Time Voice Engine

**Проект:** https://github.com/daniil7890/rvcmac
**Платформа:** macOS / Apple Silicon
**Основная тестовая машина:** MacBook Air M2, 8 GB RAM

**Главная миссия:** сделать RVCMac быстрым, естественным и стабильным нативным real-time voice conversion приложением для Apple Silicon.

**Ключевой принцип:** производительность, качество и стабильность важнее количества функций. Существующая рабочая функциональность сохраняется, регрессии недопустимы.

---

## 0. Объём релиза

**Входит в 0.3.0:**
- Этап 0 — Аудит и офлайн-харнесс.
- Этап 1 — Latency Engine.
- Этап 2 — Voice Quality.
- Этап 3 — Apple Silicon и память.
- Этап 4 — Latency Optimizer и минимальный Performance Monitor.

**Перенесено в 0.4+ (не трогать в 0.3.0):**
- Полный DSP-слой (EQ, компрессор, де-эссер, AGC).
- Voice Studio UI (Voice Library, обложки, категории).
- Voice Auto-Tuning.
- Model Compatibility Analyzer (кроме базовой проверки при загрузке).
- Multi-Voice Pipeline.
- Virtual Microphone (AudioServerPlugIn). Интеграция с BlackHole остаётся.

### 1.3. Офлайн-харнесс (обязательная часть этапа 0)

Создать режим (CLI-таргет или тестовую цель), который:

- принимает WAV, модель и параметры;
- прогоняет тот же пайплайн, что и real-time режим, блоками того же размера, но без аудиоустройства;

- детерминирован: одинаковый вход и параметры дают одинаковый выход (или различия в пределах документированного допуска, если Core ML/GPU недетерминирован).

Харнесс — основа всех дальнейших сравнений, тестов производительности и регрессий. Он не должен менять поведение основного приложения.

### 1.4. Baseline

- полная задержка и задержка каждого этапа;
- inference time, queue latency, buffer latency;

- underrun / overrun;

- GPU и Neural Engine — **по возможности** (например, через `powermetrics` с sudo). Если измерить нельзя, указать это и не тратить время.

Субъективная задержка (как её ощущает пользователь) и измеренная полная системная задержка — разные показатели, их нельзя смешивать.

## 2. Этап 1 — Latency Engine (P0)

### 2.1. Adaptive Block Size
- Поддержка нескольких размеров блока.
- Подбор выполняется только в режиме калибровки или при остановленном движке. **Смена размера блока во время обработки запрещена.**
- Оценка времени обработки и контроль underrun для каждого кандидата.
- Ручное переопределение.
- Сохранение профиля для пары «модель + устройство».

### 2.2. Dynamic Context
- Исследовать влияние размера контекста на качество (по метрикам из раздела 6) и на задержку.
- Несколько профилей.
- Без резких изменений и с сохранением непрерывности сигнала.
- Задаётся минимальный контекст для каждого профиля, ниже которого автоматика не опускается.

### 2.3. Smart Queue Management
- Ограниченная глубина входной и выходной очередей.
- Без накопления устаревшего аудио; при перегрузке отбрасывать старое, а не новое, с коротким crossfade.
- Без блокировок в real-time callback (lock-free ring buffer).
- Устаревшие фрагменты никогда не воспроизводятся.
- Приоритет: актуальность голоса и непрерывность звучания.

### 2.4. Warm-up
1. Проверить доступность модели.
2. Подготовить вычислительные ресурсы.
3. Выполнить прогрев.
4. Проверить, что выход не пустой, без NaN и в допустимом диапазоне.
5. Перевести движок в состояние READY.

Прогрев не блокирует UI.

### 2.5. SOLA (единый раздел: задержка и качество)
- Исходная реализация сохраняется как fallback и как эталон сравнения.
- Адаптивный вариант: настраиваемая длина поиска, порог корреляции, сглаживание переходов.
- Сравнить на харнессе: исходный SOLA, адаптивный, разные crossfade и окна корреляции.
- Критерии: задержка, щелчки, разрывы, металлические артефакты, поведение при резкой смене высоты.

## 3. Этап 2 — Voice Quality (P0)

### 3.1. Pitch Engine
- Уменьшить дрожание и ошибки F0, улучшить тихую речь, быстрые переходы и паузы.
- Возможна медианная фильтрация или сглаживание F0 с учётом voiced/unvoiced.
- Существующий FCPE не заменять без сравнительного теста на харнессе.

### 3.2. Protect
- Настраиваемый уровень.
- Экспериментальный адаптивный режим, отключаемый.
- Цель: естественная артикуляция и меньше артефактов на согласных.

### 3.3. Входная обработка (минимальная)
Шум, попавший в модель, превращается в артефакты, поэтому обработка ставится **до** RVC:
- Noise Gate на входе (лёгкий DSP, отключаемый).
- Limiter на выходе для защиты от клиппинга.

Без тяжёлых нейросетевых зависимостей. Остальной DSP — в 0.4+.

## 4. Этап 3 — Apple Silicon и память (P1)

### 4.1. Core ML
- Сравнить compute units: `.cpuOnly`, `.cpuAndGPU`, `.cpuAndNeuralEngine`, `.all`.
- FP16 и FP32.
- Время загрузки и компиляции модели, стоимость передачи данных.
- Переиспользование входных и выходных буферов (`MLMultiArray` / `MLShapedArray`, предвыделенные бэкинги).
- Neural Engine не считать автоматически самым быстрым — решать по замерам.

### 4.2. Accelerate / vDSP
Векторизация, FFT, ресемплинг, DSP-операции. Заменять код только при подтверждённом выигрыше на харнессе.

### 4.3. Metal
Только исследование. Переносить операции только при доказанном выигрыше.

### 4.4. Память (8 GB RAM)
- **Бюджет:** пиковая RAM приложения при одной загруженной модели — зафиксировать на baseline и не превышать; цель — снизить. Конкретное число установить после аудита.
- Минимизировать копирование тензоров, переиспользовать буферы, без аллокаций в критическом пути.
- Корректно освобождать ресурсы при переключении моделей. Проверка: 20 переключений подряд без роста памяти.

## 5. Этап 4 — Latency Optimizer и монитор (P1)

### 5.1. Latency Optimizer
1. Информация об устройстве.
2. Доступные compute units.
3. Загрузка модели и прогрев.
4. Перебор допустимых конфигураций (блок, контекст, compute units).
5. Замер задержки и стабильности (underrun).

7. Выбор и сохранение профиля.

Режимы: **Ultra Low Latency**, **Balanced**, **High Quality**, плюс возврат к ручным настройкам.

Профиль хранится для конкретной модели.

### 5.2. Performance Monitor (минимальный)
В существующем UI показывать: текущую задержку (измеренную и отдельно оценку субъективной), p50/p95/p99, inference time, queue latency, underrun, CPU/RAM. Только реальные значения, никаких заглушек.

## 6. Тестирование

### 6.1. Тестовый набор
Моно WAV по 10–20 секунд, записывает автор проекта: обычная, тихая, громкая, быстрая, медленная речь, шёпот, высокий и низкий голос, резкие переходы высоты, длинные паузы. Лежат в `TestAudio/` (в `.gitignore`, если автор не хочет публиковать голос).

### 6.2. Объективные метрики качества (на харнессе)
- **Щелчки:** детектор резких скачков амплитуды и разрывов между блоками.
- **Длительность:** выход совпадает с входом с точностью до известной задержки (нет пропусков и дублей).
- **Громкость:** RMS выхода в допуске от baseline.
- **F0:** среднее отклонение и дрожание F0 выхода относительно ожидаемого (вход + pitch shift).
- **Спектр:** mel-distance относительно baseline-выхода той же конфигурации.

Пороги фиксируются после baseline.

### 6.3. Performance
Для каждой конфигурации: p50, p95, p99, max, средний inference, queue latency, underrun, CPU, RAM. Длительный прогон — минимум 30 минут.

### 6.4. Функциональные
Запуск, загрузка и переключение моделей, смена устройств, старт/стоп движка, mute/bypass, сохранение настроек, восстановление после ошибки.

### 6.5. Регрессии
Каждое изменение аудиодвижка проверяется на харнессе: щелчки, прерывания, дубли, пропуски, громкость, тембр, задержка.

## 7. Целевые показатели

Инженерные цели, не гарантии.

| Метрика | Цель |
|---|---|
| Субъективная задержка | Сохранить преимущество, стремиться к < 90 мс |
| Измеренная полная задержка | Снизить относительно baseline |
| Underrun | 0 при штатной нагрузке |

Субъективная и измеренная задержки отображаются отдельно. Для каждой метрики — метод и условия.

## 8. Архитектурные требования

Разделение ответственности: Audio I/O, Buffer Management, Inference Engine, Pitch Engine, Voice Conversion, DSP, Model Manager, Performance Monitor, Adaptive Optimizer, UI.

Правила real-time пути:
1. В callback нет тяжёлых операций.
2. Нет блокировок (mutex, semaphore, `DispatchQueue.sync`).
3. Нет аллокаций, ARC retain/release Swift-объектов, логирования и файлового I/O.
4. Модели не загружаются в аудиопотоке.
5. Нет гонок при переключении моделей.
6. Потоки корректно завершаются.
7. Новые параметры имеют безопасные значения по умолчанию.
8. Каждый новый модуль отключается независимо.

Полная архитектурная переработка — только при доказанной необходимости и после согласования.

## 9. Правила работы Claude Code

1. Сначала изучить релевантный код, не предполагать.
2. Не удалять работающий функционал.
3. Не заменять рабочие алгоритмы без сравнения на харнессе.
4. Не переписывать проект целиком.
5. Не добавлять тяжёлые зависимости без обоснования.
6. Аудиоданные пользователя никуда не отправляются, вся обработка локальная.
7. Не менять поведение по умолчанию без необходимости.
8. Сохранять совместимость существующих конфигураций и моделей.
9. Каждое изменение аудиодвижка — с прогоном харнесса и агентом `rt-audio-reviewer`.
10. После каждого шага — сборка на Apple Silicon (`swift build -c release --arch arm64`) и `swift test`.
11. Результаты замеров — в `docs/BENCHMARKS.md`.
12. Маленькие коммиты, один логический шаг на коммит, в ветке, не в main.

При проблеме: сначала план исправления, затем минимальное безопасное изменение. Если нужна смена архитектуры — сначала альтернативы и последствия.
