## 1. Фактическая архитектура

**Модули** (`app/Package.swift`):

| Таргет | Тип | Содержимое |
|---|---|---|
| `RVCMacRT` | C | lock-free SPSC-кольцо, seqlock-часы, атомики |
| `RVCMacCore` | библиотека | статистика, телеметрия, отчёты, профили, L10n; покрыта тестами |
| `RVCMac` | executable | весь движок **и** UI: `VoicePipeline`, `VoiceEngine`, `AudioIO`, `Resampler`, `ModelLibrary`, `Diagnostics`, `AppState`, SwiftUI |
| `RVCMacTests` | тесты | только Core и RT. `VoicePipeline`, `VoiceEngine`, `AudioIO`, `Resampler`, `ModelLibrary`, `BenchmarkRunner`, `convert.py` не покрыты |

`.xcodeproj` нет. Сборка и CI идут через `swift build` и `scripts/build_app.sh`. Запуска бенчмарка в CI нет: там нет моделей.

**Роль Python: только конвертация моделей, в real-time пути не участвует [код].**

- Внешние процессы запускаются в двух местах: `AppState.swift:778-812` (`convert.py import|config|index`) и `ConverterSetup.swift:118` (создание venv, pip, tar).
- Вызываются только при импорте голоса, добавлении индекса, сборке новой latency-конфигурации и установке конвертера. Перед запуском конвертера движок останавливается (`AppState.swift:774`, `:729`).
- PythonKit и embedded Python нет; сокетов, XPC и `posix_spawn` в `app/` нет. `VoicePipeline.process` вызывает только Core ML и DSP.
- Для уже собранной пары «голос + конфигурация» Python не нужен.
- **Python нужен для каждой новой конфигурации** блок/контекст/кроссфейд, потому что формы тензоров статические (`convert.py:5`). Это главное ограничение для Adaptive Block Size и Dynamic Context (см. раздел 10.1).

## 2. Карта аудиотракта

```
 микрофон
   │  HAL IOProc входа — поток Core Audio (RT)
   │    канал 1 → mono; публикует (позиция, mHostTime)
   ▼
 inputRing — SPSC, 384000 сэмплов (8 с при 48 кГц)
   │    переполнение: режет НОВОЕ, счётчик dropped
   │
   │  RVCMac.inference — Thread, QoS userInteractive, опрос 1 мс (usleep)
   │    чтение ≤4096 → Resampler → 16 кГц
   ▼
 acc — только worker, ≥6 блоков
   │    порог «>4 блоков → выбросить старое» при блоке ≥ ~85 мс недостижим (B1)
   ▼
 VoicePipeline.process(block16)
   win[N] (контекст + блок + SOLA + кроссфейд; memmove)
   → уровень → gate
   → ContentVec ──┐ Core ML (выбранные units)
   → FCPE ────────┤ Core ML (GPU/CPU)
   → index, protect   cblas_sgemm + top-8
   → pitch, sine, noise
   → синтезатор ──┘ Core ML
   → ресемплинг в частоту выхода → SOLA → out
   ▼
 outputRing — SPSC, 384000; мягкий лимит 1,5 блока (обрезает callback)
   │    жёсткий предел: режет новое, счётчик outputOverflow
   │
   │  HAL IOProc выхода — поток Core Audio (RT)
   │    prefill ½ блока; trim без кроссфейда (A3);
   │    underrun → нули без рампы (A2); mute → рампа 5 мс
   ▼
 BlackHole / колонки
```

Смена голоса: `LoadedVoice` и `ModelState` строятся на фоне, кладутся в слот `swapLock`, worker забирает их на границе блока.

**Составляющие измеренной полной задержки** (`VoiceEngine.swift:239-261`):

```
e2e = pipeline (захват последнего сэмпла блока → воспроизведение первого)
    + algorithmic (блок + SOLA + кроссфейд − смещение SOLA)
    + device (latency + safety offset + stream latency входа и выхода)
```

Задержка ресемплеров и всего, что после BlackHole, в e2e **не входит**. У BlackHole `deviceOutputMs = 0`. Субъективная задержка кодом не измеряется и с этой величиной не смешивается.

## 6. Возможности оптимизации

Все варианты проверяются на харнессе, ожидаемый эффект — гипотеза, кроме отмеченных.

| Направление | Ожидание | Цена / риск |
|---|---|---|
| Меньше блок + кроссфейд | прямое снижение алгоритмической части: e2e −1 мс на 1 мс (формула, **[код]**) | нужны новые конвертации; ограничение по underrun |
| Контекст 300 вместо 500 мс | ContentVec и FCPE обрабатывают всё окно, ожидаем заметно меньшее время блока | качество — проверять по 6.2 |
| Прогрев при смене голоса (B6) | убирает холодный первый блок | мала |
| Compute units по этапам | Neural Engine не обязательно быстрее | мала, только замеры |
| FP16 для FCPE | перенос на ANE | есть известная проблема переполнения в Performer (`convert.py:337`) |
| Индекс: кластеризация в конвертере | заметно только на больших индексах | ниже приоритет, нужна пересборка |
| Кэширование shape/strides (B3) | мелкий джиттер | мала |
| Кэш `LoadedVoice` в RAM | мгновенная смена | противоречит 8 ГБ; P2 |

**Предел цели <90 мс.** Алгоритмическая часть равна `блок + 10 + кроссфейд − смещение SOLA`. Измеренная полная задержка ниже 90 мс недостижима при текущей схеме и блоке 100 мс: одна алгоритмическая часть там около 150 мс. Цель раздела 7 сформулирована для субъективной задержки, поэтому в отчётах эти величины показываются раздельно.

## 10. Изменения, требующие архитектурной переработки

**10.1. Статические формы моделей при адаптивном блоке и контексте.** Каждая комбинация требует конвертации через Python и места на диске (общая часть на N — 452 МБ, синтезатор — 106 МБ вместе с `.mlmodelc`). Сейчас собрано N = 10560, 12160, 13760; конфигурации b100 и b250 есть только у `gaechkatm`.

| Вариант | Плюсы | Минусы |
|---|---|---|
| А. Предсобранная сетка из 3–5 профилей на голос | без риска, совместимо с разделом 2.1 спецификации («только в калибровке») | диск, время конвертации |
| Б. Контекст через паддинг в фиксированный N | один N на все контексты | время ContentVec/FCPE не снижается |
| В. Гибкие формы (`EnumeratedShapes`) | меньше файлов | возможно, не поддерживается на ANE; **[гипотеза]**, нужен эксперимент |

**Решение (известное ограничение 0.3.0).** Формы тензоров остаются статическими. Adaptive Block Size на этом этапе выбирает только из заранее сконвертированных конфигураций (вариант А). Гибкие формы Core ML (`EnumeratedShapes`, вариант В) — отдельное исследование позже, в 0.3.0 не входят.

**10.2. Отделение движка от UI.** Необходимо для харнесса, см. раздел 11. Поведение не меняется.

**10.3. IOProc на C.** Закрывает A1 и A4. Делать только если дизассемблер покажет ARC в теле callback. Альтернатива — оставить как есть, если retain только на границе thunk.

**10.4. Компенсация дрейфа устройств.** Варианты: контроллер уровня заполнения с ресемплингом; aggregate device; ничего, пока нет замеров. Рекомендация: сначала измерить на разных устройствах.

**10.5. RT-политика и workgroup для inference-потока.** Только при подтверждённом джиттере из-за вытеснения.

**10.6. Рекомендация: CPU по умолчанию для Apple Silicon.** В код не внесена. Основание — замеры на M2 Air 8 ГБ, 100/500/50 (`docs/BENCHMARKS.md`): через 30 минут p50 блока 35,0 мс на CPU против 68,2 мс на ANE+GPU, троттлинга на CPU нет.

Ограничение: сравнение звука на всём `TestAudio` (коммит `479f8fe`, один прогон на режим) дало **FAIL по 2 метрикам из 11**: щелчки по всей записи и щелчки на границах блоков. Средние почти равны (16,6 против 16,7 и 2,4 против 2,4 на файл); FAIL вызван файлом `04_fast` и разбросом между файлами. Это значит «не доказано, что CPU не хуже», а не «CPU хуже». Все граничные щелчки в обоих режимах совпали с переходами gate.

**Условие:** рекомендация подлежит перепроверке после исправления gate, повторным сравнением на всём `TestAudio`.

**Перепроверка после исправления gate.** Граничных щелчков 0 в обоих режимах; щелчки всего 14,6 (CPU) против 14,95 (ANE+GPU), по средним по файлам правило «не хуже» пройдено 11/11. По отдельным парам (файл, сид) остаётся FAIL: одна пара `04_fast`, сид 1 (21 против 17 щелчков); на сиде 2 разность в этом файле −1. Звук на живой сессии не проверен.

**10.8. Открытые задачи.** Сейчас не делаются.
- C2: тайм-аут `stop` (3 с) оставляет работающий worker и лишний `signal` (`VoiceEngine.swift`).
- Отмена загрузки кнопкой «Стоп»: пока модели загружаются, кнопка заблокирована, отменить запуск нельзя.

**10.7. Открытые вопросы на Этап 2 (Pitch Engine).** Сейчас не расследуются.
- F0 на `03_loud` и `07_high` хуже в обоих режимах: выход ниже ожидаемых 2×F0.
- Возможные октавные ошибки pyin в самой метрике F0: окна и кадры с ошибкой около 1200 центов и более. Абсолютные значения F0 в сравнении завышены, причина не подтверждена.

## 11. Предлагаемый дизайн офлайн-харнесса (ждёт подтверждения)

**Где.** Новый executable-таргет `rvcmac-harness` (`app/Sources/RVCMacHarness/main.swift`) и новая библиотека `RVCMacEngine`.

**Почему нужна библиотека.** `VoicePipeline` и остальной движок лежат внутри executable `RVCMac`, и подключить их к другому исполняемому файлу нельзя.

| Вариант | Оценка |
|---|---|
| **А. Библиотека `RVCMacEngine`** + отдельный CLI (рекомендуется) | механический перенос файлов и `package`-видимость; движок становится тестируемым |
| Б. Режим `RVCMac --harness` | без переноса, но надо заменить `@main`, CLI линкуется с SwiftUI |
| В. Общие исходники двух таргетов | SwiftPM запрещает перекрывающиеся исходники |

Переносятся без изменения логики: `VoicePipeline`, `VoiceEngine`, `AudioIO`, `AudioDevices`, `Resampler`, `ModelLibrary`, `Diagnostics`, `ComputeChoice`. UI и `AppState` остаются.

**Минимальные дополнения к движку** (приложение их не вызывает):

1. Сброс для воспроизводимости: `resetForHarness(seed:)` (ГПСЧ, история окна и SOLA). Ресемплеры он не сбрасывает, это не требуется: выходной сбрасывается на каждом сегменте (`Resampler.segment`), входной харнесс создаёт заново на каждый прогон, а `bypassResampler` харнесс не использует. Существующий `reset()` не трогается, поскольку его вызывает `prepare()`.
2. Переопределение корня данных для CLI: у него нет `Info.plist`, и `RVCMacPaths.home` выбрал бы путь по эвристике.

**Запуск:**

```
swift run -c release --package-path app rvcmac-harness \
  --input TestAudio/normal.wav --voice gaechkatm \
  --block 100 --extra 500 --crossfade 50 --compute ane-gpu \
  --pitch 12 --index 0.75 --protect 0.33 --gate -60 \
  --device-rate 44100 --output-rate 48000 \
  --runs 3 --warmup 10 --pacing realtime --seed 1 \
  --out reports/harness/<метка>/
```

Аргументы разбираются вручную, без новых зависимостей.

**Два уровня:**

1. **Пайплайн.** WAV подаётся кусками размера буфера устройства через тот же `Resampler` и накопитель, затем в `VoicePipeline.process` блоками того же размера. Отдельный `Thread` с QoS userInteractive, как в live, и без `autoreleasepool`, как в текущем цикле; иначе baseline скроет B2.
2. **Модель очереди.** Виртуальное время: прибытие входа, измеренное время блока, чтение выхода, те же правила prefill 0,5 блока и лимита 1,5 блока. Даёт расчётные queue latency, underrun и trim. В JSON они помечены `modelled`. Модель сверяется с live-отчётом; реальную полную задержку по-прежнему даёт только live.

**Результат** в `reports/harness/<метка>/` (папка в `.gitignore`):

- `output.wav` — выход первого прогона.
- `metrics.json` — схема на основе `Report`: этапы на блок, p50/p95/p99/max, холодный старт, CPU, пиковая RAM (`phys_footprint` и lifetime max), наклон памяти МБ/блок, термостатус, параметры, коммит.
- `blocks.csv` — построчно по блокам.

**Детерминизм.** ГПСЧ сбрасывается по `--seed` после прогрева. Ожидаем побитовое совпадение на CPU **[гипотеза]**. Для GPU/ANE допуск измеряется 5 прогонами (максимум и RMS разности) и документируется по каждому режиму.

**Длительный прогон.** `--loop-minutes 30` зацикливает файл. GPU/ANE — отдельный скрипт с `sudo powermetrics` рядом с запуском, необязательно.

**Проверка, что поведение приложения не изменилось:** `swift test`; сборка `.app`; сравнение выхода и времени этапов до и после переноса.

**Шаги (коммиты):**

1. Перенос в `RVCMacEngine`, без изменения логики.
2. CLI: уровень пайплайна, WAV, JSON, CSV.
3. Детерминизм и замер допуска.
4. Модель очереди и сверка с live.
5. Baseline: заполнение раздела 5 и создание `docs/BENCHMARKS.md`.

Метрики качества 6.2 (щелчки, F0, mel-distance) подключаются отдельно, перед Этапом 1.
