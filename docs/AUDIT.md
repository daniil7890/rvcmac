# Аудит аудиотракта RVCMac

Фаза 0 по `RVCMac_Specification_Improvements_RU` (п. 14, 16). Ниже описано, как устроен тракт, какие проблемы нашлись в версии 0.1.0 и что исправлено в этой ветке. Цифры задержки здесь не приводятся: их дают отчёты из окна «Диагностика».

## 1. Карта тракта

```
 микрофон
   │  HAL IOProc входа (поток Core Audio, real-time)
   │    • канал 1, interleaved → mono
   │    • публикует (позиция в кольце, mHostTime первого сэмпла)
   ▼
 inputRing  ── lock-free SPSC, 2×192000 сэмплов, при переполнении режет новые данные (счётчик)
   │
   │  поток RVCMac.inference (QoS userInteractive), опрос раз в 1 мс
   │    • чтение кусками ≤4096 → Resampler (AVAudioConverter, частота устройства → 16 кГц)
   │    • накопитель acc16; если отстали больше чем на 4 блока, старое аудио выкидывается (счётчик)
   ▼
 VoicePipeline.process(блок 16 кГц)
   1. окно N = (контекст + блок + SOLA + кроссфейд) × 160 сэмплов, сдвиг memmove
   2. уровень входа → порог тишины (gate)
   3. ContentVec (Core ML, units пользователя)            → stage contentvec
   4. FCPE (Core ML, GPU/CPU, fp32) + декодирование f0    → stage pitch_fcpe
   5. index: cblas_sgemm + top-8, ×2 апскейл, protect     → stage features_index
   6. coarse pitch, NSF-синусоида, шум prior              → stage excitation
   7. синтезатор RVC (Core ML)                            → stage synth_rvc
   8. ресемплинг sr модели → частота выхода, SOLA         → stage output_sola
   ▼
 outputRing ── lock-free SPSC; лишнее сверх 3 блоков выкидывает сам колбэк вывода (счётчик)
   │
   │  HAL IOProc выхода (real-time)
   │    • prefill полблока перед стартом
   │    • публикует (позиция чтения, mHostTime буфера)
   │    • underrun → тишина + счётчик
   │    • mute / push-to-talk: рампа ~5 мс, без щелчка
   ▼
 выход (BlackHole / колонки)
```

**Алгоритмическая задержка.** Синтезатор декодирует последние `блок + SOLA + кроссфейд` кадров окна. Блок вывода берётся с начала этого участка со смещением SOLA, хвост длиной кроссфейда остаётся до следующего блока. Поэтому выходной сэмпл отстаёт от своего входного на `(блок + 10 мс + кроссфейд) − смещение SOLA`, то есть на 250–260 мс при блоке 150 мс и кроссфейде 100 мс. К этому добавляются обработка, очередь вывода и задержки устройств. Ощущение «около 90 мс» из спецификации с этой арифметикой не сходится, его нужно перепроверить замером.

## 2. Найденные проблемы (версия 0.1.0)

| # | Где | Проблема | Риск | Статус |
|---|-----|----------|------|--------|
| 1 | `AudioIO.swift`, `FloatFIFO` | Колбэки Core Audio брали `OSAllocatedUnfairLock`, а worker держал тот же лок | инверсия приоритетов: колбэк ждёт поток более низкого приоритета | заменено на lock-free кольцо на C11 atomics (`RVCMacRT`) |
| 2 | `AudioIO` выход | `[weak self]` в колбэке, неатомарные `outputStarted` и `outputPrefill` | гонка данных и загрузка weak-ссылки в real-time потоке | колбэк захватывает только готовые объекты, флаги атомарные |
| 3 | `VoiceEngine.loop` | `EngineStats.underruns` нигде не увеличивался | underrun были не видны | считаются события и кадры underrun, переполнения, обрезки, пропуски |
| 4 | `VoiceEngine` | Индикатор показывал только максимум времени `process()` | нет полной задержки и разбивки по этапам | 8 этапов на каждый блок, p50/p95/p99, задержка от захвата до вывода |
| 5 | `VoiceEngine.loop` | `outputFIFO.trim` вызывал worker, то есть производитель | нарушение SPSC, гонка с чтением колбэка | обрезает сам потребитель (колбэк) по атомарному лимиту |
| 6 | worker | На каждом блоке аллокации: `Array(acc16[...])`, `removeFirst` у массивов, `floats()`, `dots` (Q×M, при большом индексе это мегабайты), буферы `AVAudioPCMBuffer` в ресемплере, `MLDictionaryFeatureProvider` | джиттер времени блока | буферы и feature providers создаются один раз; во время работы аллокации остаются только внутри Core ML |
| 7 | `VoiceEngine.stop` | Поток не дожидался выхода, его ресурсы освобождались, пока шёл инференс | редкие гонки при быстром старт/стоп | `stop()` ждёт завершения блока (тайм-аут 3 с) |
| 8 | `AudioIO` | Отключение устройства и смена частоты не обрабатывались | тишина без объяснения или неверный ресемплинг | слушатели `IsAlive` и `NominalSampleRate` останавливают или перезапускают аудио с сообщением, `ProcessorOverload` считается |
| 9 | `AppState.appendLog` | Файловый I/O на главном потоке на каждую строку лога | подвисания UI при длинной конвертации | запись в файл на отдельной utility-очереди |
| 10 | `buildFeatures` | Пустой индекс (`M = 0`) ронял приложение на `max()` | краш | индекс используется только при `M > 0` |
| 11 | конвертер | `torch.load(..., weights_only=False)` для пользовательского `.pth` | `.pth` — это pickle, он может выполнить код (п. 12 спецификации) | по умолчанию `weights_only=True`; полная загрузка только с `--unsafe-pickle` после явного подтверждения в приложении |
| 12 | входной колбэк | Буферы больше 16384 кадров молча обрезались | потеря аудио без следа | обрезка считается (`truncatedCallbacks`) |

Математику DSP (ContentVec, FCPE, index, NSF, SOLA) я намеренно не трогал, чтобы baseline старой и новой версии был сравним (п. 15: «не менять несколько подсистем за один эксперимент»). Заметки на потом:

- после блока, отрезанного порогом тишины, `solaBuffer` остаётся от старого голоса, и следующий блок начинается с кроссфейда от этого хвоста. Нужно проверить на слух, нужен ли сброс;
- поиск по индексу — точный перебор O(Q·M). При индексах больше ~100k векторов этап `features_index` будет виден в разбивке. Кандидаты на оптимизацию: IVF или кластеризация в конвертере, сгемм на ANE через Core ML.

## 3. Как снимать baseline

1. Собрать **старую** версию (тег `v0.1.0`) и **новую** с одинаковыми настройками: модель, блок 150 / контекст 500 / кроссфейд 100, вычисления «Neural Engine + GPU».
2. **Файловый тест** (Диагностика → Бенчмарк). Один и тот же WAV (лучше реальная речь, 20–60 с), 3 прогона, реальный темп включён, Mac на зарядке. Отчёт сохраняется как `reports/bench-*.json` и `.csv`.
3. **Live-тест.** Микрофон → BlackHole, 10 минут речи, затем «Сохранить отчёт сессии». Для приёмки — 60 минут (п. 12): смотреть, что `underrun` не растёт, память стабильна, p99 полной задержки не уплывает.
4. **Сравнение.** Вкладка «Сравнение» показывает A/B по p50/p95/p99 этапов и предупреждает, если конфигурации различаются.
5. **Эксперименты с размером блока** (п. 5.2): 150 → 120 → 100 → 80 мс, на каждом свой бенчмарк и 10-минутный live. Размер блока уменьшается только пока p99 обработки ниже блока с запасом и нет underrun.

Для GPU и ANE публичного API нагрузки процесса нет. Отчёты так и пишут, а смотреть её предлагается в Instruments (шаблоны Core ML и Metal System Trace).

## 5. Первые замеры (MacBook Air M2, Neural Engine + GPU)

| Шаг | Полная p50 | Конвейер | Алгоритмическая | Устройства |
|-----|-----------|----------|-----------------|------------|
| 150/500/100, логика v0.1.0 (очередь до 3 блоков) | 699 мс | 279 | 258 | 163 |
| + прогрев моделей до старта, очередь ≤ 1,5 блока | 548 мс | 131 | 254 | 163 |
| 100/500/50, выход в BlackHole | 321 мс | 115 | 152 | 51 |

Главная находка — стоячая очередь вывода около 230 мс. Первые блоки на холодном Neural Engine считаются медленно, вход за это время копится, и этот хвост оставался в очереди на всю сессию. Обработка блока при этом около 50 мс (p95 66 мс) при блоке 100 мс. Следующий кандидат — контекст 300 мс: ContentVec и FCPE обрабатывают всё окно.
