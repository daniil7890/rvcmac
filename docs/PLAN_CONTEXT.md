# План эксперимента «контекст 300»

Статус: **только план**. Конвертация не выполнялась, движок не менялся. Дата: 14.11.2026.
Основание: живые замеры b80/64 и b100 (`docs/BENCHMARKS.md`), запрет b50 при контексте 500
(`docs/AUDIT_030.md`, размен A2 / цена блока).

## 1. Цель

Цена блока задаётся контекстом, а не длиной блока: block_total p50 при b80 — 27.4 мс против
27.2 мс при b100 (контекст 500 в обоих). При b50_e500 оценка p99 ≈ 49 мс при бюджете 50 мс —
запаса нет, b50 запрещён. Уменьшение extra 500 → 300 сокращает окно (block + extra) с 580 до
380 мс (для b80) и, по оценке, p99 с 51.9 до ~38 мс. Цель: найти минимальный контекст, который
держит абсолютный порог качества и даёт запас по времени блока для b50 (ниже алгоритмическая
задержка).

## 2. Адаптивная стадийность

Полная сетка заменена адаптивной: каждая следующая стадия зависит от результата предыдущей,
лишние конвертации не делаются.

**Стадия 1 — b80_e300 (одна конвертация).**
- Держит качество (абсолютные гейты раздела 3, калиброванные пороги раздела 6) и
  p99(block_total) ≤ 64 мс (0.8 × 80) → стадия 1b: b50_e300.
- Не держит → fallback **b80_e400** (одна конвертация), решение по нему.
- **b100_e300/e400 отложены**: референс b100_e500 уже есть, промежуточные точки не нужны
  до решения по b80/b50.

**Стадия 1b — b50_e300** (если стадия 1 прошла): гейт p99 ≤ 40 мс (раздел 5);
прошёл → кандидат на целевую конфигурацию.

**Стадия 2 — b50_e300_cf30** (после решения по сетке cf50): кандидат на целевую задержку —
алгоритмическая ~85 мс против ~105 мс у cf50 (блок 50 + кроссфейд 30/50 + SOLA ≈ 5).
Сравнение cf30 с cf50 — **отдельное, после решения по сетке**: кроссфейд влияет на стыки и
SOLA, смешивать его эффект с эффектом контекста нельзя.

Сетка cf50 не меняется (аргумент про конфаунд принят): при b50 cf50 == block — граница
клампа D3; cf > block внёс бы кламп-конфаунд в сравнение.

Голос gaechkatm (референсный), pitch 12, index 0.75, protect 0.33, gate −60 — как в
quality-baseline. Режимы: CPU и ANE+GPU. Сиды 1 и 2. Весь TestAudio (10 файлов), pacing fast,
warmup 10. На стадию 1: 1 × 2 × 2 × 10 = 40 прогонов.

## 3. Протокол качества: абсолютные метрики

Существующие пороги (`BENCHMARKS.md`, «Пороги качества») подобраны как **разности против
выхода 100/500/50** и кросс-конфигурационно не применимы: выходы разных конфигураций легитимно
различаются (другой контекст → другой сигнал), и разность измеряла бы различие конфигураций,
а не регрессию. Поэтому сравнение МЕЖДУ конфигурациями — только по абсолютным метрикам,
каждая конфигурация проверяется независимо.

**Жёсткие гейты (на файл, абсолютные):**
- `bound_clicks = 0` и `bound_jumps = 0` — щелчки/скачки на границах блоков (определения из
  `scripts/quality_gate.py`). Это главный критерий: контекст не должен ломать стыки.

**F0 относительно входного сигнала (не относительно выхода другой конфигурации):**
- pyin по входу и по выходу; кадры, voiced в обоих; ошибка в центах:
  `err = 1200·log2(f0_out/f0_in) − 100·pitch` (pitch 12 → ожидаемое удвоение).
- Метрики: медиана |err|, p95 |err|, доля |err| > 50 центов, доля |err| > 600 центов
  (октавные обороты — отдельно, см. ограничение ниже).
- Предлагаемые абсолютные пороги (предложение, калибровать после замера референса e500 этим
  же протоколом): медиана |err| ≤ 50 центов, доля |err| > 100 центов ≤ 10%. Пороги фиксируются
  до прогонов кандидатов, чтобы не подгонять под результат.

**Наблюдаемые (без гейта):** клики суммарно, gain_db относительно входа, len_err, gaps,
алгоритмическая и pipeline-задержка конфигурации, распределение block_total.

**Гейт производительности:** p99(block_total) ≤ 0.8 × blockMs в целевом режиме на всём
TestAudio; max и число блоков сверх бюджета — в отчёт.

**Правило одиночного срабатывания:** нарушение на одном сиде → проверка на втором;
считается только повторившееся (оба сида прогоняются сразу).

## 4. Чего этот протокол НЕ доказывает

- **Перцептивное качество, тембр, похожесть на спикера** — нет прослушивания и нет
  speaker-embedding метрики; абсолютные F0 и стыки доказывают только корректность высоты и
  отсутствие граничных артефактов.
- **Что e300 «не хуже» e500** — эквивалентность конфигураций не устанавливается; протокол
  проверяет абсолютный пол, а не сравнительное качество. Разный контекст может звучать
  по-разному при одинаковых абсолютных метриках.
- **Живая стабильность** — тепловые режимы, underrun на реальных устройствах, дрейф,
  длинные сессии: офлайн-харнесс этого не видит.
- **Валидность самой F0-метрики** — pyin даёт октавные ошибки (аудит 10.7); доля оборотов
  > 600 центов может отражать ошибку метрики, а не конверсии.
- **Обобщение на другие голоса/питчи/языки** — один голос, pitch 12.

## 5. Оценка времени блока при extra 300 (по текущим замерам)

Метод: стадии живой сессии b80_e500 (окно 580 мс, 10036 блоков) масштабируются:
contentvec/synth/features ∝ окну (block + extra), f0/excitation ∝ блоку, resample/sola —
константы. Это **линейная модель-оценка**, не замер: фиксированные расходы Core ML и
нелинейность внимания не учтены; после конвертации обязательно проверить фактом.

| Конфигурация | Окно, мс | Оценка p50 | p95 | p99 | max | Бюджет |
|---|---|---|---|---|---|---|
| b80_e500 (замер) | 580 | 27.4 | 37.4 | 51.9 | 561.3 | 80 |
| b80_e300 | 380 | 20.1 | 27.3 | 37.9 | ~372 | 80 |
| b80_e400 | 480 | 23.8 | 32.4 | 45.1 | ~467 | 80 |
| b50_e300 | 350 | 16.8 | 22.9 | 31.7 | ~339 | 50 |
| b50_e400 | 450 | 20.5 | 28.1 | 39.1 | ~434 | 50 |

- b80_e300: p99 ~38 мс при бюджете 80 — запас ~2×.
- b50_e300: p99 ~32 мс при бюджете 50 — запас ~1.6×; редкие всплески (max ~340 мс, contentvec)
  дадут единичные underrun, закрытые рампами A2.
- **Порог запрета b50: b50 запрещён, если замеренный p99(block_total) > 40 мс** (80% бюджета
  50 мс — нет запаса на джиттер); при p99 > 50 мс underrun систематические. Оценка b50_e400
  p99 ~39 мс — пограничная, решение только по замеру.

**Оговорка к модели:** масштабирование fcpe ∝ блоку спорно — питч считается по окну
(fcpe видит весь контекст), а не по блоку, и при уменьшении блока доля fcpe может не упасть.
Оценка p50 16.8 мс для b50_e300 — **оптимистичная граница**: f0/excitation могут остаться на
уровне b80. Решение только по замеру после конвертации.

## 6. Нулевая калибровка F0-протокола (14.11.2026, без конвертаций)

Скрипт `scripts/f0_vs_input.py` (конвенции `quality_gate.py`: 16 кГц pyin C2..C6, кадр 1024 /
hop 160, resolution 0.1, lag-выравнивание 0..200 мс по минимуму медианы |err|). Данные:
эталон e500 (`reports/quality-baseline-e725643`), 10 файлов, CPU и ANE+GPU, сиды 1/2.
Результаты по файлам: `reports/f0-calibration/<mode>/<file>-{zero,abs1,abs2,inter}.json`.

| Проверка | CPU | ANE+GPU |
|---|---|---|
| zero: выход против самого себя, pitch 0 | медиана 0.0, октавы 0, gt100 0 (все 10) | то же |
| abs: сид 1 против входа, pitch 12 | медиана: среднее 24 / max 70 центов; октавы 4.0% / max 15.9%; gt100 13.3% / max 39.1% | 26 / 90; 5.0% / 21.9%; 14.9% / 46.0% |
| abs: сид 2 против входа | 25 / 80 | 26 / 80 |
| inter: сид 2 против сида 1, pitch 0 | медиана 9 / max 10 центов; октавы 0; gt100 2.1% / max 7.2% | 9 / 10; 0; 2.0% / 6.2% |
| Межсидовый разброс абсолютных медиан | среднее 1 / max 10 центов | среднее 2 / max 10 центов |

**Выводы:**
1. Нулевое сравнение даёт ровно 0 — реализация протокола корректна.
2. Межсидовый шум (≤ 10 центов по медиане, октавных оборотов 0) существенно ниже порога
   50 центов → **протокол пригоден** для сравнения конфигураций: деградация от контекста
   величиной > 10–20 центов отличима от шума метрики.
3. Предложенные абсолютные пороги (медиана ≤ 50, gt100 ≤ 10%) **не проходят сам референс**:
   gt100 в среднем 13–15%, до 39–46% на `03_loud`; медианы до 70–90 центов. Это не шум
   метрики (межсидовый разброс мал), а реальное отклонение F0 на проблемных файлах
   (аудит 10.7) плюс октавные ошибки pyin на стороне входа. Пороги калиброваны по
   референсу и фиксируются до прогонов кандидатов: на файл — медиана ≤ 90 центов,
   gt100 ≤ 0.46, октавы ≤ 0.22; в среднем по 10 файлам — gt100 ≤ 0.15; на «чистых» файлах
   (кроме `03_loud`/`07_high`) — медиана ≤ 30 центов.
